# ライセンス・公開対象管理の開発計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** MIT改変版の公開に必要な帰属・第三者通知を整え、実データと認証秘密を公開対象から除外する。

**Architecture:** コード、公開許諾を確認したサンプル、非公開の運用データ・秘密を分ける。
第三者素材をMITへ一括変更せず、配布する版のライセンス条件を追跡する。
Git追跡対象と実際の配布物の両方を検査する。

**Tech Stack:** Git、既存GitHub Actions、Docker、Pythonの標準ライブラリ、既存ReactのAbout画面。

**Spec:** `docs/superpowers/specs/2026-10-24-semantic-studio-customization-design.md` 第11節。
根拠と調査限界は `docs/license-publication-review.md`。

## Global Constraints

- 原LICENSEのImran Khan氏の著作権表示・MIT全文・免責を保持する。
- 第三者素材の条件をMITで上書きしない。改変者の帰属は実際の権利者確認後に追記する。
- 実データ・認証秘密はpublicリポジトリ/配布物へ含めない。CIは合成データで動く。
- 許可Workspaceドメインは非公開の運用設定であり、公開コードの利用資格ではない。
- 本計画作成は公開操作の実行ではない。新しい監査サービスへのデータ送信は行わない。
- 本計画は横断的な追加作業。P1全体の実装計画やP2認証設計の代わりではない。
- 各作業は、その成果物の配布より前に完了する。P1でDocker/文書ZIP等を配布する場合は、
  Task 4の通知・混入確認とTask 5を先に実施し、P3到達まで先送りしない。

## Review Focus

- 無視設定の追加前にGit追跡/履歴へ入ったファイルも公開前の確認対象となる（Task 2/5）。
- 実データを別名・Turtle・ZIPへ変換しても公開対象にはならない（Task 2/4/5）。
- frontendの環境変数に入れた秘密はビルドへ埋め込まれ得る（Task 3）。
- GitHubでは除外できてもDocker contextやReleaseに実データが入る可能性を扱う（Task 2/4）。
- ライセンス不明をMITとして処理せず未確認として公開を止める（Task 1/4）。

## Task 1 — P1：帰属と第三者通知

**Interfaces:** 第三者通知の各行は、対象パス/パッケージ、対象版、出典URL、ライセンス、
通知の保存先、確認状態を記す。状態は確認済み/未確認。未確認は公開可とみなさない。

- [ ] 実際の改変部分の権利者と問い合わせ先を確認する。組織名を推測しない。
- [ ] 元LICENSEを保持し、READMEに非公式改変版と対象範囲を明記する。
- [ ] npmのlockfileとPythonの配布時解決版から直接/推移依存を列挙し、原文/NOTICEを確認する。
- [ ] WordNet、標準語彙、同梱例の個別条件と改変有無を台帳に記録する。
- [ ] 必要な全文とNOTICEを収録する。ソースの通知とデータの通知を区別する。
- [ ] 版と通知が対応する依存物一覧を生成し保存する。固定していないPython依存は、
  配布時に解決した版と推移依存の一覧を保存し、実際の配布物との一致を検証する。
- [ ] Aboutの帰属・上流リンク・改変版リンクを分け、日英表示に対応する。
- [ ] Aboutの既存テストを更新し、元作者とMITの保持、改変版の区別を確認する。
- [ ] 第三者通知と対象ファイルを照合し、不明素材は公開前に除外または条件確認する。

## Task 2 — P1：Git・Dockerへの混入防止

**Interfaces:** `python scripts/check_publication.py --git-ref REF` は指定コミットの
Git blobを検査する。`--staged` はindexのblobを検査する。どちらも作業ツリーの内容へ
置き換えず、対象を一つ明示する。問題がなければ終了0、候補があれば1、読み取り失敗・
未対応形式・上限超過・未許可の例外等で確認を完了できなければ2とする。
`--root PATH --files-from LIST` は配布物・テスト用の相対パス一覧を受け取り、
LISTはNUL区切り。Gitモードとの併用、絶対パス、root外への脱出を拒否する。
診断は安全にエスケープしたパスとルール名のみとし、秘密の値を出力しない。
終了0は「指定内容が定義済みルールに抵触しない」という意味で、網羅的な秘密検出や
未知の業務データの識別を保証しない。未検査ファイルを黙って読み飛ばさない。

`publication-policy.json` は `version: 1`、`public_samples`、`exceptions` を持つ。
公開サンプルはpath/source/license/sha256を記録し、例外はpath/rule/reasonを一件ずつ記録する。
例外は包括的なディレクトリ除外ではなく対象ルールだけに適用し、他の秘密検査を免除しない。
この公開許可表はデータセットや非テキスト配布物の追加に適用し、通常のソース変更ごとの
ハッシュ事前登録を要求するものではない。業務データは名称を変えて許可表へ登録しない。

- [ ] 禁止対象に `test_data/`、`.env`/`.env.*`、`.aws/`、秘密鍵、OAuthクライアント秘密、
  セッション/トークン保存物、ユーザーの元Excel/JSONと変換データ、試験画像・ログを含める。
  公開用の `.env.example` はダミー値だけとし、実データと区別する。
- [ ] `.gitignore` と `.dockerignore` を整備する。既存の利用者の変更を消さない。
- [ ] 検査の回帰テストに、禁止ファイル、別名のMongoDB元レコード、RDF内の元JSONと
  内部コメント、ダミー秘密鍵、実秘密形式のダミー値を入れ、非0終了を確認する。
  検知すべき値はテスト実行時に一時ディレクトリで組み立てる。負のfixture自体を
  Gitへ丸ごと格納して検査から除外する方式にしない。
- [ ] 同じテストで合成RDF、ライセンス、ダミー設定例は通り、診断に値が出ないことを確認する。
- [ ] Gitのindex/指定コミットに禁止内容、作業ツリーに無害な内容を置いた一時repoで、
  検査が実際に送信するblobを読んで失敗することを確認する。スペース/改行入りパスも検査する。
- [ ] 公開許可したWordNet等のサンプルは元ライセンス付きで通ることを確認する。
  合成RDFも含むすべてのRDF/JSONを禁止する実装にはしない。
- [ ] ZIPはroot配下でメンバーを展開せず検査し、元ファイル名とメンバーの診断を分ける。
  ZIPの深さは1、メンバー数は1,000、各ファイルは20MiB、読取総量は100MiBを上限とする。
  通常ファイルも1件20MiB、全体100MiBまで。上限超過・暗号化・リンク・未対応バイナリは
  終了2とし、画像等の必要素材はハッシュを固定した許可表と目視確認で別に扱う。
  検査対象や上限を変える場合は方針ファイルと根拠をレビューする。
- [ ] 元データの特徴/禁止パスと秘密候補を組み合わせて検査し、改名だけで回避できないようにする。
  許可例外が必要なら対象と理由を明示してレビューする。
  項目名が文書/コードにあるだけで禁止せず、構造化レコード等の具体的な特徴で判定する。
  台帳の変更を伴わない検査器の内容検知範囲拡大は、正負のfixtureを併せてレビューする。
- [ ] `python -m unittest discover -s scripts -p 'test_check_publication.py'` で回帰確認する。
- [ ] CIへ組み込み、クリーンなチェックアウトだけで実行できることを確認する。
- [ ] CIでは検査器自体の回帰テストを走らせた後、イベントの固定SHAを `--git-ref` で検査する。
  未信頼PRで資格情報を使わず、`pull_request_target` と未信頼コードの組合せを採用しない。
  変更ファイルの検査だけで既存履歴の監査が済んだとは表示しない。
- [ ] 実際のDocker contextとCOPY対象にも禁止データが入らないことを検査する。

## Task 2a — P1：公開可能なアプリ試験データ

**Interfaces:** `backend/tests/synthetic_dictionary.py` の
`build_synthetic_organizations(count: int = 3035) -> rdflib.Graph` は外部ファイルも
ネットワークも読まず、固定規則から `https://example.org/synthetic/` 配下の個体を生成する。
`count` は正の整数。P1の画面試験用にはこのグラフから作業用Turtleを生成し、
実データのコピーを使わない。WordNetの公開サンプルはライセンス確認のうえ別に利用できる。

- [ ] 同入力で同じトリプル集合になること、3,035個体を生成すること、
  代表名/別名/読み/検索用語/文字列IDと説明欠落例が存在することをテストする。
  別IRIの同名概念、ラベルだけの資源、未宣言クラスの個体、長い表示名・IRIも少数生成する。
- [ ] 生成器を実装し、元の組織名・元ID・コメント・raw JSONを一切転用しない。
- [ ] `python -m pytest tests/test_synthetic_dictionary.py` をbackendで実行し、
  件数・一意ID・検索に必要な値・生成の決定性を確認する。
- [ ] P1の検索・一覧API試験で、2,000ノードを超える個体をすべてページ送りできること、
  別名/読み検索と欠損説明、UI応答に内部原本が含まれないことを検証する。
- [ ] フロントのモックと実ブラウザ試験も同じ規則の合成データを使う。

## Task 3 — P2：認証情報の取り扱い

**Interfaces:** 公開OAuthクライアントID・許可ドメインと、クライアント秘密・セッション鍵・
トークンを分ける。採用する認証フローで不要な秘密は追加しない。

- [ ] 必要な秘密はサーバーの実行環境または秘密管理機構から供給する設計にする。
- [ ] frontendの `VITE_*`、ソースコード、設定例、保存済みブラウザ状態へ秘密を入れない。
- [ ] 認証エラーやHTTPログへ資格情報・Cookie・トークン本文を出さない。
- [ ] 認証のテストは模擬トークン/ダミー鍵を使用し、本番資格情報に依存させない。
- [ ] ビルド/ログの検査でダミー秘密マーカーが混入しないことを確認する。

## Task 4 — 各段階の配布前、およびP3/P4/P5：配布物と追加データ

**Interfaces:** 配布対象ごとに、素材一覧と必要通知を記録する。
Gitソース、Dockerイメージ、フロントビルド、文書ZIP、辞書公開版を別々に確認する。

- [ ] コード・依存物・データに必要なライセンス/NOTICEが各配布物に含まれることを確認する。
- [ ] Dockerfileが通知を置くパスを実際にCOPYすること、フロント/文書ZIPから必要通知へ
  到達できることを配布物で確認する。リポジトリrootに通知を追加しただけで完了としない。
- [ ] 辞書の公開用出力は項目の許可リストで生成し、内部コメント/元JSON/秘密は除去する。
- [ ] 現行の文書ZIPは元の入力ファイルを `source/original.*` に保存するため、
  画面の個体非表示を公開データ除去とみなさない。公開用経路を別に設け、
  ソース同梱を含む全エントリを許可済みのグラフから生成する。原本保持の既存出力は
  内部向けと明示して維持し、公開用と混同しない。P3実装前は内部実データの文書ZIPを配布しない。
- [ ] `projects.export_zip` もプロジェクト原本の内部バックアップとして維持し、
  公開版生成に流用しない。公開用の全出力は固定した許可済みグラフからのみ生成し、
  元ファイル・プロジェクト設定・クエリ・スナップショット原本を追加しない。
- [ ] 非公開のダミーマーカーを含む合成データから公開出力を作り、除去を回帰確認する。
  ZIPのすべてのメンバー、埋め込みHTML/JSON/グラフ、Turtleにマーカーがないことを検査する。
- [ ] WordNet全件の追加や依存更新ごとに版・出典・条件・変更有無を更新する。
- [ ] 専用インポーターで読み込んだ実データを、リポジトリ内の公開サンプルへ自動保存しない。

## Task 5 — public化・Release前の確認

- [ ] 実際に公開するブランチ/全到達可能履歴、追跡ファイル、Release添付、Actions成果物、
  Docker/文書ZIP/画像に非公開データと秘密がないか確認する。候補の値はログへ出さない。
- [ ] PRブランチへのpushもpublic repoでは公開である。送信先の固定base/head SHAと
  差分パス、送信によって新たに到達可能になるコミットをpush前に確認する。
  一覧のない無制限なファイル追加・無関係なローカルコミットを混ぜない。
- [ ] 第三者台帳の未確認事項と、配布物に必要な通知の欠落がないことを確認する。
- [ ] 秘密を発見した場合は公開を止め、失効・再発行を優先する。
  削除コミットだけで履歴から消えたと判断しない。履歴書き換えは影響を別途レビューする。
- [ ] 公開対象と検査結果を確認し、ユーザーが指定した公開操作の範囲で進める。
  push/PRが明示的に依頼された場合は再度の一律承認を求めない。
  ブロッカーがあれば影響範囲を報告し、repoの公開範囲変更やmergeは別の操作として扱う。

## 計画の自己確認

P1で通知と混入防止の基盤、P2で認証秘密、P3以降で出力と追加素材を扱い、
最後に実際の公開対象を確認する。実装・全履歴監査が完了したとは主張しない。
この計画の作成時点ではアプリのLICENSE本文や公開設定は変更しない。
ライセンス通知と公開対象検査は配布物ごとに前倒しし、実装完了前に公開可と表示しない。
